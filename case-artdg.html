01이관과 구조

상품 135개를 새 구조로 옮겼습니다

범위는 옛 상품을 새 구조로 옮기고, 손님이 상품을 찾아 수량을 계산하고 장바구니에 담게 하는 것이었습니다. 상품 데이터는 옛 사이트 DB에서 가져왔습니다.

상품 135개, 안내 페이지 5개, 묶음 할인 규칙 2종, 상품정보 응답 52~170ms입니다.

02구조와 설계 결정

값을 바꾸는 쪽, 보는 쪽, 주문하는 쪽을 나눴습니다

지금 사이트가 돌아가는 구조와, 왜 이렇게 나눴는지입니다.

운영 값을 바꾸는 쪽

  1. 관리자접근 제한 + 서버에서 토큰 재검증
  2. 설정 저장소 (D1)초안 · 변경 이력 · 버전
  3. 발행 절차검증 후 정적 파일 생성

공개 방문자가 보는 쪽

  1. 콘텐츠 원본 (JSON)상품·분류·안내·규칙
  2. 정적 사이트 (Next.js)빌드 시점에 화면 생성
  3. Cloudflare Workers정적 파일 배포

주문 장바구니와 결제

  1. 브라우저장바구니는 기기에만 저장
  2. API Worker주문 등록 · 상품정보 응답
  3. 네이버페이연동 완료

  1. 공개 화면과 주문 처리를 나눴습니다

    화면은 정적 파일이라 빠르고, 문제가 나도 화면 전체로 번지지 않습니다. 주문 API가 없으면 구매는 닫힌 채로 있습니다. 실패해도 잘못 열리지 않는 쪽으로 기울였습니다.

  2. 관리자는 한 겹 더 막았습니다

    접근 제한 뒤에 두고, 서버에서도 토큰을 다시 검증합니다. 주문 접수를 한 번에 끄는 스위치가 있습니다.

  3. 값을 바꾸는 절차를 남겼습니다

    저장은 초안이고, 발행해야 사이트에 반영됩니다. 변경 이력이 남고, 두 곳에서 동시에 고치면 한쪽이 덮어쓰지 못하게 버전으로 막습니다.

  4. 가격 기준을 한 곳에 뒀습니다

    팔지 말지 정하는 곳, 관리자 입력, 주문 데이터가 같은 하한을 씁니다. 원본가의 50% 아래로는 내리지 않고, 한 번에 깎는 폭은 25%까지입니다. 화면마다 기준이 달라져 가격이 어긋나는 일을 막으려고입니다.

  5. 중복 주문을 막았습니다

    같은 구매에는 같은 키를 붙입니다. 탭이 여러 개여도 등록은 한 번에 하나씩입니다. 결과가 애매하면 다시 넣지 않고, 확인해 달라고 안내합니다.

  6. 배포 실수를 먼저 막았습니다

    코드가 뒤처졌거나 커밋하지 않은 변경이 있으면 배포가 시작되지 않습니다. 단위 테스트, 계약 테스트, 화면을 눌러 보는 테스트, 운영 문서가 같이 있습니다.

03관리자와 안전장치

운영자가 관리자에서 값을 고칩니다

상품과 규칙을 여기서 고칩니다. 저장만 하면 초안이고, 발행해야 손님 화면에 나갑니다. 발행할 때마다 기록이 남습니다.

관리자 화면 범위

상품·옵션, 카테고리, 판매 기준, 구매 규칙, 묶음 할인, 배송, 안내·법적 표기, 사업자 정보, 페이지·리다이렉트, 발행, 연결 점검.

이 목록은 코드를 보고 확인했습니다. 아래 영상과 화면 5장은 운영 화면을 직접 열었고, 나머지는 눌러 보지 않았습니다.
